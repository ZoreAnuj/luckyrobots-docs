# swiftui-arch

## Key findings
- The 2025-2026 SwiftUI architecture consensus for small/solo apps has shifted away from heavyweight MVVM toward a lightweight 'MV' pattern: @Observable (Observation framework, iOS 17+) service/store objects injected via @Environment, views reading state directly with @State/@Bindable. @Observable gives per-property access tracking so only views reading a changed property re-render; MVVM-with-coordinators is considered warranted only at 50+ screens / 3+ engineers, which does not apply to a solo personal app.
- HealthKit itself should be treated as the source of truth for all health/workout/sleep data — do not mirror it wholesale into a local database. A local store is only needed for app-native domain data (nutrition/food logs, RPG/XP state, settings, cached daily summaries for widgets). This drastically shrinks the persistence layer.
- For that small local store, SwiftData is adequate for a single-user personal app (native, @Query SwiftUI integration, zero boilerplate), while GRDB is ~20x faster on inserts and adds FTS5 and SQLCipher — overkill here. SwiftData still has known limitations (it wraps Core Data; historical iOS 17/18 migration and predicate bugs documented by Fatbobman), so keep models simple and avoid complex relationships. Plain Codable JSON files are a legitimate third option for tiny state like avatar/XP.
- Canonical HealthKit sync architecture: HKObserverQuery registered with healthStore.enableBackgroundDelivery(for:frequency:) wakes the app when new samples arrive; the observer's updateHandler then runs an HKAnchoredObjectQuery (or its async HKAnchoredObjectQueryDescriptor) with a persisted HKQueryAnchor to fetch only the delta (new + deleted samples). Anchored queries CANNOT themselves be registered for background delivery — the observer+anchored pair is mandatory. You MUST call the observer query's completionHandler after handling the update or iOS will throttle and eventually stop background deliveries.
- Deduplication of iPhone-vs-Watch double counting (steps, active energy) is solved by using HKStatisticsQuery/HKStatisticsCollectionQuery (or their async descriptors) with .cumulativeSum — HealthKit merges overlapping sources exactly as the system Health app does. Summing raw HKSampleQuery samples yourself WILL overcount. Use .separateBySource only when you need per-source breakdown.
- Modern HealthKit has full async/await query descriptors: HKSampleQueryDescriptor, HKAnchoredObjectQueryDescriptor (results(for:) returns an AsyncSequence you 'for try await' for long-running live updates), HKStatisticsCollectionQueryDescriptor (Results async sequence), and HKQuantitySeriesSampleQueryDescriptor for high-resolution per-second heart rate series. These fit Swift 6 concurrency cleanly and eliminate callback plumbing.
- HealthKit authorization is asymmetric by design: you can never detect that READ permission was denied — denied reads just look like empty data. requestAuthorization's success bool only means the sheet was presented, not that access was granted. authorizationStatus(for:) only reports SHARE (write) status. Use getRequestStatusForAuthorization(toShare:read:) to decide whether to show the request sheet, and show a pre-permission explainer screen; design empty states that say 'no data or access not granted — check Settings > Health > Data Access'.
- Simulator reality: the HealthKit API surface works in the simulator but the store is empty (no Watch, no sensors), background delivery does not fire, and workout routes/sleep are absent. Practical workflow: build a debug-only seed-data generator (HKWorkoutBuilder + saving quantity samples) for simulator/UI work, but do all real testing on device — which is also required anyway for free-provisioning sideloading.
- Free personal team (sideload) constraints confirmed: HealthKit and App Groups capabilities ARE available to personal teams; push notifications, and most other special entitlements are NOT. Provisioning profiles expire every 7 days (app stops launching until re-run from Xcode), max 3 sideloaded apps, ~10 new App IDs per rolling week. The com.apple.developer.healthkit.background-delivery entitlement (required iOS 15+ for enableBackgroundDelivery) is a standard HealthKit capability checkbox — but background delivery is best-effort: system may skip updates on low battery, requires Background App Refresh enabled, and never fires if the user force-quits the app.
- Background delivery frequency is capped per data type: many types (including steps/activeEnergy) are limited to .hourly minimum wake interval regardless of asking for .immediate; heart rate and workouts support .immediate. Design the dashboard to refresh on foreground (scenePhase .active) as the primary path, with background delivery as opportunistic pre-warming.
- Swift Charts is the right viz layer: LineMark/AreaMark for trends, BarMark with yStart/yEnd (min/max) for Health-app-style heart-rate range bars, RuleMark for goal lines, PointMark for workout scatter. iOS 17+ adds .chartScrollableAxes(.horizontal) + .chartXVisibleDomain(length:) + chartScrollPosition for Apple-Health-style paging charts. Performance: pre-aggregate/downsample data before charting (e.g., HR to ~1 sample per 5-15s per workout chart) and avoid per-second whole-chart re-renders.
- TimelineView(.everyMinute) is the idiomatic way to keep a dashboard's time-relative content ('as of 9:41', ring progress) fresh without timers; combine with .refreshable and scenePhase-triggered re-query for data freshness.
- GPS route rendering (Strava-like): fetch HKWorkoutRoute via HKSampleQuery/HKAnchoredObjectQueryDescriptor with HKQuery.predicateForObjects(from: workout) on the workoutRoute() series type, then stream CLLocation batches with HKWorkoutRouteQuery; render with SwiftUI Map + MapPolyline(coordinates:) with stroke styling, and MapCameraPosition fitted to the route's bounding rect. Route data is written automatically by Apple Watch outdoor workouts, so the app needs no location tracking of its own for historical routes.
- Widgets: App Groups are the only supported app↔widget data channel. A widget extension CAN query HealthKit directly if the main app holds authorization, BUT the Health store is unavailable while the device is locked (data protection), so lock-screen/StandBy widgets fail there. Standard pattern: main app (foreground + background delivery wakes) writes a compact daily-summary snapshot (steps, kcal, ring %, XP/level) to the shared App Group container, calls WidgetCenter.shared.reloadAllTimelines(), and the widget's TimelineProvider just renders the snapshot with graceful 'last updated' staleness display.
- Live Activities (ActivityKit) work fully with LOCAL updates (Activity.request / activity.update) — no push entitlement needed, so they are compatible with free provisioning; a workout Live Activity updating from an in-app workout session is feasible. Constraints: 4KB content state limit, update-budget throttling for high-frequency updates (NSSupportsLiveActivitiesFrequentUpdates Info.plist key raises the budget), Dynamic Island compact/expanded/minimal presentations defined in the widget extension via ActivityConfiguration.
- Testability approach that survives HealthKit's untestable singleton: wrap HKHealthStore behind a small protocol (e.g., HealthReading with async funcs returning domain structs), so ViewModels/stores are tested with a stub returning fixture data via Swift Testing; keep all metric math (TDEE, recovery score, XP calculation, streaks) in pure free functions or small structs with zero HealthKit imports — these become the most-tested code in the app.
- Recommended app structure for dashboard+detail: single Xcode project, one local Swift Package with multiple targets (modularization via local SPM is the 2026 standard, but for solo scale keep it to 4-6 targets, not per-feature explosion). NavigationStack with a Router/@Observable navigation model; TabView or a single scrolling dashboard with NavigationLinks into detail screens (Workout detail, Nutrition day, Sleep detail, Avatar/RPG screen).
- Observer queries and anchored-query anchors have documented flakiness (Apple forums: anchored queries silently stop receiving updates after long runs; background delivery observed firing only while charging on some iOS versions) — architecture should be self-healing: on every foreground activation, re-run all anchored syncs from persisted anchors rather than trusting long-lived query callbacks.

## Specifics
- @Observable macro (Observation framework, iOS 17+) replaces ObservableObject/@Published; inject stores with .environment(store) and read via @Environment(HealthStore.self); use @Bindable for two-way bindings to @Observable objects
- HealthKit read types needed for this app: HKQuantityType(.stepCount), .activeEnergyBurned, .basalEnergyBurned, .heartRate, .restingHeartRate, .heartRateVariabilitySDNN, .vo2Max, .respiratoryRate, .distanceWalkingRunning, .bodyMass, .dietaryEnergyConsumed, .dietaryProtein/.dietaryCarbohydrates/.dietaryFatTotal, HKCategoryType(.sleepAnalysis) with iOS16+ sleep stages (asleepCore/asleepDeep/asleepREM/awake), HKObjectType.workoutType(), HKSeriesType.workoutRoute(), plus watchOS-11-era HKQuantityType for apple sleeping wrist temperature if desired
- Sync pipeline: healthStore.enableBackgroundDelivery(for: type, frequency: .immediate) → HKObserverQuery(sampleType:predicate:) updateHandler → run HKAnchoredObjectQueryDescriptor(predicates:[.sample(type:)], anchor: savedAnchor).result(for: healthStore) → persist new anchor (NSKeyedArchiver archive of HKQueryAnchor, requiringSecureCoding: true, stored in UserDefaults/file) → call observer completionHandler()
- Entitlements: com.apple.developer.healthkit (capability checkbox), com.apple.developer.healthkit.background-delivery (iOS 15+ required for enableBackgroundDelivery); Info.plist: NSHealthShareUsageDescription and NSHealthUpdateUsageDescription (both mandatory or instant crash on request)
- Authorization APIs: healthStore.requestAuthorization(toShare:read:) — bool result ≠ granted; healthStore.getRequestStatusForAuthorization(toShare:read:) returns .shouldRequest/.unnecessary to gate the sheet; authorizationStatus(for:) only meaningful for share/write types; HKHealthStore.isHealthDataAvailable() guard at launch
- Dedupe: HKStatisticsCollectionQueryDescriptor(predicate:options:[.cumulativeSum], anchorDate:intervalComponents: DateComponents(day:1)) merges Watch+iPhone sources automatically = matches Health app numbers; .separateBySource for per-device breakdown; never sum raw step samples
- Async descriptors: HKSampleQueryDescriptor(predicates:sortDescriptors:limit:).result(for:), HKAnchoredObjectQueryDescriptor.results(for:) → AsyncSequence for live updates, HKStatisticsCollectionQueryDescriptor.results(for:), HKQuantitySeriesSampleQueryDescriptor for per-second HR within a workout
- Background delivery frequency caps: stepCount/activeEnergy limited to .hourly max; heartRate/workout support .immediate; requires Background App Refresh ON; skipped on low battery; dead after force-quit; simulator never fires background delivery
- Workout routes: HKAnchoredObjectQueryDescriptor over HKSeriesType.workoutRoute() with HKQuery.predicateForObjects(from: workout) → HKWorkoutRouteQuery(route:) streams [CLLocation] in batches with a 'done' flag → SwiftUI Map { MapPolyline(coordinates: coords).stroke(accentColor, style: StrokeStyle(lineWidth:4, lineCap:.round)) } with MapCameraPosition.region fitted to route bounds
- Swift Charts marks for fitness: BarMark(x:.value("Day",date,unit:.day), yStart:.value("Min",hrMin), yEnd:.value("Max",hrMax)) for HR range bars; AreaMark with .interpolationMethod(.catmullRom) + LinearGradient for pace/HR fills; RuleMark(y:.value("Goal",goal)) with .foregroundStyle + annotation for goal lines; SectorMark (iOS 17+) for macro pie/donut
- Health-app-style scrolling: .chartScrollableAxes(.horizontal), .chartXVisibleDomain(length: 3600*24*7), .chartScrollPosition(x: $scrollDate), .chartXSelection(value:) for scrub-to-inspect lollipop
- TimelineView(.everyMinute) for dashboard clock/progress recompute; TimelineView(.animation) only for live workout gauges; .refreshable pull-to-refresh; onChange(of: scenePhase) == .active triggers full anchored resync (self-healing sync)
- Widget data flow: App Group container (group.com.yourname.fitness) → shared JSON snapshot struct (DailySummary: steps, activeKcal, consumedKcal, ringPct, level, xp, lastUpdated) written by main app → WidgetCenter.shared.reloadAllTimelines() → TimelineProvider reads snapshot; widget HealthKit reads fail when device locked, so always render cached snapshot with timestamp
- Live Activities: ActivityAttributes + ContentState (≤4KB), Activity.request(attributes:content:), activity.update(ActivityContent(state:staleDate:)), local updates need no push entitlement (works on free provisioning); NSSupportsLiveActivitiesFrequentUpdates=YES for workout-frequency updates; Dynamic Island via ActivityConfiguration(for:) { lockscreen } dynamicIsland: { compact/expanded/minimal }
- Free provisioning: profiles expire 7 days (rebuild from Xcode weekly, or automate with ios-deploy/Xcode CLI), 3 concurrent sideloaded apps, ~10 App IDs/week, HealthKit + App Groups allowed, push notifications/iCloud NOT allowed → no CloudKit sync, no remote Live Activity pushes; design app as fully offline/local
- Persistence split: HealthKit = system of record for workouts/steps/HR/sleep/weight and even nutrition totals (write dietaryEnergyConsumed etc. back to HealthKit); SwiftData @Model for FoodEntry, MealTemplate, XPEvent, AvatarState, GoalSettings; @Query in views for SwiftData, no mirroring of HealthKit samples except lightweight cached daily aggregates keyed by date for chart speed
- Testing: protocol HealthKitReading { func dailySteps(on: Date) async throws -> Double ... } implemented by live HKHealthStore wrapper and by FixtureHealthStore in tests; pure logic modules (XP/level curve, streaks, TDEE, recovery score from HRV/RHR/sleep) as dependency-free structs tested with Swift Testing (@Test macros); debug-only simulator seed screen using HKWorkoutBuilder to fabricate workouts
- Module breakdown (local SPM package 'FitnessKit' with targets): 1) Models (pure domain structs, zero imports), 2) HealthService (HKHealthStore wrapper, observer/anchored sync engine, anchor persistence), 3) Persistence (SwiftData models + stores), 4) GameEngine (XP/levels/quests, pure logic), 5) DesignSystem (colors: cream #F5F0E8-ish bg, coral accent #D97757, spacing tokens, typography, reusable cards/rings), 6) app target with Features folders (Dashboard, WorkoutList/WorkoutDetail, Nutrition, Sleep, Recovery, Avatar) + Widget extension target sharing Models+DesignSystem
- Known flakiness to engineer around: HKAnchoredObjectQuery long-running updates silently stop (Apple forums thread 776209); background delivery sometimes only fires while charging (thread 812200); mitigation = stateless resync-on-foreground from persisted anchors as primary mechanism, background delivery as bonus

## Recommendations
- Adopt MV-style architecture: @Observable 'store' objects (HealthStore, NutritionStore, GameStore, SyncEngine) injected via .environment(); no ViewModels-per-screen, no TCA. Views read stores directly; heavy logic lives in pure, testable structs beneath the stores.
- Treat HealthKit as the database for all health data (including writing nutrition entries back as dietary samples so Apple Health stays canonical); use SwiftData only for app-native data: food entry metadata/meal templates, XP events, avatar state, goals, and a small cached daily-aggregate table for instant dashboard/chart loads.
- Build one SyncEngine actor implementing: enableBackgroundDelivery + HKObserverQuery per type → anchored delta fetch via HKAnchoredObjectQueryDescriptor → persist HKQueryAnchor → update caches → reload widgets; AND a full resync-on-foreground path from the same anchors, because observer/background delivery is unreliable. Always call the observer completion handler.
- Use HKStatisticsCollectionQueryDescriptor with .cumulativeSum for steps/energy so numbers match the Health app (automatic Watch/iPhone dedupe); never sum raw samples.
- Plan for free-provisioning constraints from day one: no push, no iCloud/CloudKit — everything local; expect weekly re-install from Xcode (7-day profile expiry); HealthKit, App Groups, WidgetKit, and locally-updated Live Activities all work fine on a personal team.
- Ship the dashboard with Swift Charts (scrollable iOS-17 Health-style charts, BarMark yStart/yEnd HR ranges, RuleMark goals), TimelineView(.everyMinute) for time-fresh content, and MapKit MapPolyline over HKWorkoutRoute for Strava-like route cards — all first-party, zero dependencies, matching the minimal aesthetic.
- Widgets: share a compact DailySummary snapshot through an App Group written by the main app and reload timelines after each sync; never have the widget query HealthKit as its primary path (locked-device failures).
- Wrap HKHealthStore behind a protocol and keep game/metric math dependency-free so Swift Testing covers the interesting logic; add a debug-only HealthKit seed-data screen for simulator development, but validate sync/background behavior on the real iPhone+Watch.
