# Lucky Engine Docs

The documentation site for **Lucky Engine**, organized by engine system. The first section,
**Scripting**, covers the C# scripting API: hand-written guides plus an API reference
generated directly from the engine's `Hazel-ScriptCore` source. Future systems (rendering,
editor, simulation, the Python SDK) become sibling sections under `docs/`.

Built with [Material for MkDocs](https://squidfunk.github.io/mkdocs-material/). The API
reference is generated by a small Roslyn-based tool (`tools/ApiDocGen`) from C# `///` doc
comments, so it never drifts from the code.

This is a **standalone repository** — it reads the engine's C# source from a separate
Lucky Engine checkout (configurable path, env var, or CI checkout). Nothing here depends on
being inside the engine tree.

## How it works

```
LuckyEngine/Hazel-ScriptCore/Source/**.cs
        │   tools/ApiDocGen  (Roslyn: parse public API + /// doc comments)
        ▼
docs/scripting/api/**.md   ← generated (gitignored)
docs/**.md                 ← hand-written guides (committed)
        │   mkdocs build  (Material theme)
        ▼
site/                      ← static HTML   (deployment: coming soon)
```

## Prerequisites

| Tool | Version | For |
|------|---------|-----|
| [.NET SDK](https://dotnet.microsoft.com/) | 9.0+ | running the `ApiDocGen` generator |
| [Python](https://www.python.org/) | 3.10+ | MkDocs / Material |
| A local Lucky Engine checkout | — | source of the API reference |

## Quick start (local preview)

```powershell
# 1. One-time: create the Python environment
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# 2. Generate the API reference and serve with live reload,
#    pointing at your engine checkout:
.\scripts\serve.ps1 -Source C:\Dev\LuckyRobots\LuckyEngine\Hazel-ScriptCore\Source
```

Then open <http://127.0.0.1:8000>. Editing a guide hot-reloads; re-run
`.\scripts\generate.ps1` after changing engine source to refresh the reference.

To avoid passing `-Source` every time, set `$env:LUCKYENGINE_SCRIPTCORE` or create a
machine-local `tools/ApiDocGen/apidocgen.local.json` (see [The generator](#the-generator-toolsapidocgen)).

## Writing docs

- **Guides** — author Markdown directly under `docs/scripting/`. The nav is built
  automatically from the folder tree and `.pages` files, so there's no hand-maintained nav
  to keep in sync.
- **API reference** — never hand-edited; it's a build artifact. To change reference text,
  edit the `///` XML doc comment on the type or member in the engine source, then re-run
  `.\scripts\generate.ps1`.

**Adding a new engine system** later is just a new sibling folder under `docs/` (e.g.
`docs/rendering/`) with its own `.pages` — it becomes a new top-level tab automatically.

## The generator (`tools/ApiDocGen`)

A .NET 9 console tool that parses the `.cs` files **syntactically** (no engine build or
dependency resolution required) and emits one Markdown page per public type, grouped into
categories, with cross-references resolved to relative links.

Run it directly:

```powershell
dotnet run --project tools/ApiDocGen -c Release -- --root . --source <Hazel-ScriptCore\Source>
```

**Source path resolution order:** `--source` → `$LUCKYENGINE_SCRIPTCORE` →
`sourceRootCandidates` in `apidocgen.config.json`. For a machine-local source path that
isn't committed, create `tools/ApiDocGen/apidocgen.local.json` (gitignored):

```json
{ "sourceRootCandidates": ["C:/Dev/LuckyRobots/LuckyEngine/Hazel-ScriptCore/Source"] }
```

**Scope** is controlled by `apidocgen.config.json`: `excludeNamespaces` /
`excludeFileGlobs` / `excludeTypeNamePatterns` keep internal plumbing (gRPC, interop,
generated code) out of the docs, and `categories` maps source folders to the sections you
see in the nav.

## Continuous integration

`.github/workflows/docs.yml` runs on every push / PR to `main`: it checks out the engine,
generates the reference, and runs `mkdocs build --strict` (fails on any broken link or
anchor). No deploy.

## Deployment

The live site at **<https://docs.luckyrobots.com>** is a Cloudflare Worker (static assets).
CI builds the versioned site with [mike](https://github.com/jimporter/mike) and uploads it;
`wrangler.jsonc` binds the custom domain (same Worker `name`/routes as the legacy
`luckyengine-doc` repo, so this repo simply takes it over).

### Versioning model (mike)

Each maintained version owns its own long-lived branch and one slot on the `gh-pages` branch:

| Branch | Publishes | Alias | Dropdown title | Default? |
|--------|-----------|-------|----------------|----------|
| `release/2026.1` | `2026.1/` | `stable` | `2026.1` | ✅ (`/` lands here) |
| `release/2026.2` | `2026.2/` | `preview` | `2026.2 (Preview)` | |

The mapping lives in [`.github/versions.json`](.github/versions.json). Versions are **not**
parallel folders — your `docs/` tree is always one version; mike snapshots it into the
matching slot on `gh-pages` and maintains the dropdown's `versions.json`.

### Publishing

- **Update a live version** — commit to its `release/<version>` branch (regenerate the API
  reference first if engine source changed) and push. CI republishes *only that version's
  slot* and redeploys; other versions are untouched.
- **Add a new version** — create `release/<version>`, add an entry to
  `.github/versions.json`, push.
- **Republish manually** (e.g. fix an old version) — Actions → **Docs** → *Run workflow*,
  enter the version label.

What CI does on a release push: strict `mkdocs build` → `git fetch` existing `gh-pages` →
`mike deploy --push --update-aliases <version> <alias>` (+ `mike set-default` if it's the
default) → export `gh-pages` to `./_site` → `wrangler deploy`.

### One-time setup

- Repo secrets **`CLOUDFLARE_API_TOKEN`** and **`CLOUDFLARE_ACCOUNT_ID`** (same values the
  old repo used; a token with *Workers Scripts: Edit* on the `luckyrobots.com` account).
- Create the `release/<version>` branches.
- After the first successful deploy from here, stop deploying the old `luckyengine-doc`
  repo (disable its workflow) — both target the same Worker.

### Local preview

`mkdocs build` outputs to `site/`; `mkdocs serve` live-previews (see the
[quick start](#quick-start-local-preview)). To preview the *versioned* build locally,
`mike deploy <version>` (without `--push`) then `mike serve`.
